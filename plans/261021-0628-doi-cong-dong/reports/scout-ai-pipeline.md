## 2. "Soi đội từ ảnh" pipeline

VERIFIED
- It is a **separate Worker `worker/`** (`worker/wrangler.toml`: name `tqccl-vision-proxy`, same KV id `6fff7d73…` as community AI_KV, binding named `RL`). Endpoint `POST /analyze` only (`worker/src/index.ts:58-60`), JSON body `{image: base64|dataURI, turnstileToken, mode}`. Gate: CORS origin, `IP_HASH_SECRET`, body size, per-IP KV rate (`RL_PER_HOUR=10`, `DAILY_CAP=500`, `MONTHLY_CAP=8000`, `ratelimit.ts`), **Turnstile one-time token** (:110), size/MIME guard (`guard.ts`). **No user auth.** Group `teamScan` for mode `analyzeTeamImage` (`index.ts:28`).
- Browser caller: `js/analyze.js:208` fetch to `ANALYZE_CONFIG.workerUrl` = `https://tqccl-vision-proxy.nguyennlt-ncc.workers.dev/analyze` (`js/config.js:6`), Turnstile sitekey `js/config.js:8`; `callWorker(imageDataUrl, token, mode)` :228.
- **Yes, it extracts TACTICS per hero.** Contract (`worker/README.md` table; `worker/src/schema.ts:5-40`): `{ screen:"battleReport"|"teamDetail"|"other", sides:[{side:"left"|"right", heroes:[{nameCn, tacticsCn[≤3 rows], booksCn[], statFocusCn}]}] }`, 1–2 sides, ≤6 heroes/side. Simplified-Chinese **names**, not ids; unreadable cell = `"未知"` at the same position; `tacticsCn` includes the hero's self-carried tactic as the first row ("worker does not classify"). Other modes: `scanHeroes`, `scanTactics`, `scanBuiltTeams` (`{teams:[{teamName,heroesCn[],tacticsCn[]}]}`), `explainSubstitute`.
- **Name→id mapping is client-only**, `js/analyze-map.js`: `normalizeTeamRead` :283, `draftFromRead` :252 (drops self tactic via `selfTacticCn` from heroes dict, `learnedTacticRows` :236-244; 2 learned slots = `TACTIC_SLOT_COUNT` :30), `classifyName`/`createEntityIndex` :164-208 over `js/match-dict.js` fuzzy matcher (Levenshtein, `DEFAULT_THRESHOLD 0.7`, ambiguity margin). Output cell `{state:"sure"|…, raw, id, candidates}`; `draft.heroes[3]` × `{hero, tactics[2], book}` (`TEAM_SIZE=3`). Editor draft is exactly the "3 heroes × 2 tactics" shape the feature needs.
- `community-worker/src/routes/scan.ts` is NOT a scanner: only anonymous stats `/api/scan-stats` (:122), user sample upload `/api/scan-samples` (:188; multipart image + `payload` JSON with `aiRead` and `confirmed` whose hero/tactic ids are regex-checked only, `ID_RE` :24-28), and admin review/fixture export. Rate `scan_sample` 10/day (`ratelimit.ts:108`).
- Callable from community-worker? **No binding today**: `community-worker/wrangler.jsonc` has only DB, MEDIA, AI_KV, FEEDBACK_MAIL (no `services`). Reaching `worker/` would need a service binding (or public fetch) AND would hit its Turnstile/IP-hash gates (CORS/Origin check passes only with Origin header; Turnstile token is browser-issued, one-time) — impractical server-to-server. `worker/src/*` is not importable as a shared module (separate package; only `shared/ai-config.ts` + `shared/ai-models.ts` are shared, imported as `../../../shared/…`). The prompt for `analyzeTeamImage` lives in `worker/src/model.ts` (image_url at :84) — INFERENCE: could be copied/shared to `shared/` but not required.

## 3. Hero/tactic id validation and data availability

VERIFIED
- `validate.ts:48-56` `parseHeroes`: 1–20-char **free-text names**, ≤5, no dupes; no id check. `PAGE_KEY_RE` (`validate.ts:5`) only allows `/(doi-chuan|doi-khac|khai-hoang)/<slug>/` → must be extended to `doi-cong-dong` (numeric/ulid id) for comments namespace.
- Only id validation in worker: regex `^hero:[a-z0-9]+(?:-[a-z0-9]+)*$` / `tactic:` / `book:` (`scan.ts:24-28`, `parseId` :53) — shape only, existence NOT checked.
- Source of ids: `data/heroes-dict.json` (251 heroes, 568 KB, fields `id:"hero:sp-gia-cat-luong"`, `chinese`, `viet`, `hanViet`, `aliases`, `faction`, `cost`, `roleTag`, `selfTacticCn`, `troopApt{cung,khiGioi,ky,thuan,thuo…}`, `iconUrl`); `data/tactics.json` (409 tactics, 826 KB, `id:"tactic:…"`, `chinese`, `viet`, `type`, `troopFit`, `quality`); the site loads them via `js/lookup-data.js:1,299-300` (verified against `data/lookup-manifest.json`); `pipeline/lookup-client-heroes.json`/`-tactics.json` and `data/lookup-catalog.json` (advisors/equipment/troopMods; 347 KB) are other client payloads. Total ids chars for hero+tactic ≈ 12.9 KB (computed).
- **Not available in community-worker at runtime**: grep shows community-worker/src imports only `shared/*`; no import of any data JSON (searched `heroes-dict|lookup-client` in community-worker/src + test: none). Data exists only as static site files (`data/…` served to browser). Hero names in `heroes-dict` are also keyed zh as `chinese` (traditional) with simplified in `aliases`.
- Existing posts ids: `battle_reports` stores names, `scan_samples` stores ids (unvalidated). Id-by-locale rendering therefore must be done on client from the dicts (already done everywhere else on the site).

## 4. Recommendation (INFERENCE, grounded above)

**Option A (recommended): new endpoint in community-worker, new schema, client does name→id mapping with existing `analyze-map.js`.**
- Add `POST /api/community-teams/analyze` modelled on `reports.ts:90-135` (login, FEATURE_ENABLED kill switch, rate-limit key e.g. `team_analyze`, `parseImageUpload`, store pending R2 upload kind e.g. `team` so the same image can be attached on submit) but with a **team prompt/parser** (new `analyzeTeamImage`-like function in a new file, e.g. `community-worker/src/analyze-team.ts`) returning the **same shape as `worker/` `analyzeTeamImage`** (`sides/heroes/nameCn/tacticsCn`) so `normalizeTeamRead` + `draftFromRead` (`js/analyze-map.js:283,252`) are reused unchanged. Route group: reuse `teamScan` (vision-capable, already admin-configured with a chain; its prompt is team-scan oriented) — zero admin work. Reusing `battleReport` would also work but its group is meant for battle reports. Adding a new AI group costs admin UI work and an empty chain at first.
- Server returns names only; client maps to ids with local dicts (fuzzy, needs the user to confirm "unsure" cells — same UX as `/soi-doi-tu-anh/`). Server then validates submitted ids by shape (regex like `scan.ts:24-28`) and—if strict existence is wanted—needs an id allow-list: generate a small build artefact (e.g. `community-worker/src/generated/lookup-ids.json`, ≈13 KB of ids, hero+tactic) from `data/heroes-dict.json`/`data/tactics.json` in the build/deploy step, because the Worker has no data. Without it, bad ids can only be rejected by shape (client-trust; XSS-safe if rendered via dict lookup with unknown-id fallback).
- Costs/limits: one vision call per image, ≤ 20/day/user shared with `analyze` limit if same key (recommend separate key to avoid starving battle reports); image ≤ 1.5 MB (client downscales to 1600px JPEG ~0.82, `js/community-api.js:246`); AI timeout/budget from the group (`MAX_BUDGET_MS=180000`, `shared/ai-config.ts:69`); 422 unreadable → empty draft, user fills manually; 502/503 → no upload kept.

**Option B: reuse `worker/` from browser** (client calls `workerUrl` with Turnstile exactly like `/soi-doi-tu-anh/`). Pro: zero server code, exact same contract. Con: not under community-worker's login/rate limit/FEATURE_ENABLED (it has its own IP limit 10/h, global caps 500/d, 8000/mo shared with Soi đội), requires Turnstile on the form, and the image still has to be uploaded separately to R2 (two uploads). Spec said "reuse existing pipeline (rate limit + FEATURE_ENABLED)" → this partly misses auth-based limits.
**Option C: server→`worker/` service binding** — rejected: Turnstile/CORS/IP gating make it unusable; would require modifying `worker/`.
